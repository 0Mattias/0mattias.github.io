Building bettermemory

Persistent memory for AI coding agents, retrieved on demand rather than pre-loaded.

May 18, 2026 · updated August 15, 2026

bettermemory is a local MCP server (and a Claude Code plugin). Memory lives as plain markdown on disk and gets exposed through tools the model calls when it actually needs context. Nothing is injected into the prompt per turn, and when the model does pull a memory in, the contract is to say so in the reply.

The failure mode

The shape most memory features ship with is the same: stored facts get pre-loaded into every conversation. Run that for a few weeks and two patterns show up. The first is bleed-through. Memory pulled in for an unrelated topic still tints tone, framing, and assumptions; the model is doing what you’d expect when irrelevant context lands in the prompt, and the bug is the design choice that puts it there. The second is silent staleness. A fact stored in March still sits in the prompt in November, after the file paths moved or the project changed direction, and the model treats it as fresh.

The two failures are not symmetric. False negatives are recoverable: the model forgets, you tell it again. False positives cascade: the model anchors on a stale fact, builds reasoning on top, and you don’t see the moment the conversation went off. So bettermemory retrieves nothing by default. “Walk me through pandas from zero to hero” is worth a search, because a stored learning-style preference could shape the answer. “How do I write a list comprehension” is not, and no search runs.

The verdict

Memory is a snapshot; it does not refresh itself. So every retrieval folds three signals into a single staleness verdict: how long since anything confirmed the fact, whether the file paths it cites still exist on disk, and how many commits have landed in the repo since it was last checked. A memory verified three months and two hundred commits ago is fresh on the calendar and stale everywhere it counts, and the hit says so before the model leans on it.

A flagged hit isn’t discarded, it’s checked. The model re-reads the repo, fixes what drifted, and attests to what it verified. Freshness is earned back, never assumed.

Plain files

There is no database. Every memory is a markdown file with YAML frontmatter: greppable, diffable, hand-editable, backed up with cp, synced across machines with git because there is nothing else to sync.

---
id: 01HXYZ123ABCDEFGHJKMNPQRST
created: 2026-03-14T10:23:00+00:00
scopes: [tools, learning-style]
confidence: high
source: explicit-statement
---
When I ask for a "zero to hero" tutorial, I want a hands-on
walkthrough with code I can run, not a tour of the IDE.

Everything the project has grown since — attribution down to the sentence a memory shaped, audits that flag the searches the model should have run but skipped, a gate that keeps pasted secrets off disk, an eval that publishes how often memory actually helped with the unflattering numbers included, a public postmortem owed whenever a verdict misleads an agent — reads and writes those same files. The format is the API.

In practice

Day one, you say something durable:

When I ask for a tutorial, I want runnable code, not screenshots of an IDE.

A claim about you never commits on its own; Claude asks first, then the file lands. Week two, “walk me through pandas from zero to hero” surfaces the preference, announced out loud: “Using your stored preference for code-driven tutorials…” Month three, “what’s the difference between find and fd?” is generic, so no search runs, and the reply isn’t tinted by months of accumulated context.

Install, for Claude Code:

/plugin marketplace add 0Mattias/bettermemory
/plugin install bettermemory@bettermemory

For any other MCP client: uv tool install bettermemory, then bettermemory init --client <name>. Source on GitHub ↗. MIT.
